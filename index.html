Ranking Content for Review: A Baseline-vs-Model Study on Search Performance Data

Does a trained model beat a simple, transparent scoring rule at telling a content reviewer which pages to look at first — and can that improvement survive an honest test?

Muhammad Raza · Final-year Computing Systems, Ulster University London · Repository

Abstract

Summary

Content teams cannot manually review every page they publish, so they need a defensible way to decide which pages to look at first. This project frames that choice — refresh, investigate, or leave alone — as a ranking problem, using FlyRank's anonymized content-performance dataset (30,000 pages, 32 clients). A transparent rule-based baseline was built first, verified against two independently-audited signals (staleness and CTR-vs-position), then compared to a Random Forest model trained on the same features. Under a client-grouped validation split — which holds entire clients out of training to prevent the model from memorizing client-specific patterns — the model reached a precision@50 of 0.66, roughly double the baseline's 0.30. The same model scored an inflated 0.75 AUC under a naive random split, a 0.17-point gap that demonstrates why validation design, not just model choice, determines whether a result can be trusted. The result is a ranked, explainable action playbook, not a guarantee: it is decision-support for a human reviewer, not a causal claim about what refreshing any single page will do.

01

Introduction

A content library grows faster than any team can manually audit it. The question this project answers is not "is this page good or bad," but a narrower, more useful one: which pages should a reviewer with limited time look at first?

The decision this work supports: a content or SEO reviewer, working through a ranked queue, decides where to spend a fixed review budget — typically the top 20 to 50 pages a cycle allows. Getting this wrong has an asymmetric, real cost. A false positive wastes a reviewer's limited time on a page that didn't need attention. A false negative lets a genuinely declining, still-visible page keep losing ground unnoticed until the next cycle.

A simple hand-written rule can flag a handful of conditions — stale and popular, declining and visible, ranked well but under-clicked. But a rule can only combine a few conditions with fixed logic; it cannot learn how signals interact. This project tests whether a model earns its added complexity by actually outperforming that rule, under a validation design honest enough to trust the answer.

This mirrors a problem FlyRank's own product already solves at scale, assigning pages priority flags like "needs refresh" or "fix CTR" across a portfolio too large for manual review. This project rebuilds that decision from first principles, using only observable signals rather than the product's existing rules, to test whether a learned ranking can outperform a transparent baseline on the same problem.

02

Data

This project uses two FlyRank internship data sources, at different stages of the work:

  • Starter dataset (content_refresh_anonymized.csv) — 30,000 pseudonymized content items across 32 clients, trailing-90-day search and engagement metrics. This is the primary dataset used for baseline construction, modeling, and validation throughout this paper.
  • Warehouse release (Hugging Face, FlyRank/internship-warehouse) — used in an early data-contract exercise to verify grain, coverage, and availability on real production-scale data (a single month, March 2026, ~9.8M daily rows), and to practice defining a leakage-safe label from raw signals rather than a pre-computed field.

Rows were filtered to content with at least some search demand (impressions_90d > 0) and at least 90 days of age, then deduplicated to one row per content item — verified directly rather than assumed.

What was deliberately excluded

  • Product-computed scores (e.g. a health_score or priority_score) — not present in this dataset, and would represent a circular result if used: the model would learn to copy an existing rule instead of discovering real signal.
  • Client and content identifiers — used only for joining and grouped validation splits, never as predictive features, since the pseudonymized codes carry no real-world meaning.
  • Any field computed from the label itself (e.g. trend_pct, when the label is derived from trend_direction) — caught directly during this project's own work, described in Methodology below.
03

Methodology

Label

The target is is_declining_label, defined as trend_direction == "down". This is a same-window proxy — derived from the current observation window rather than a genuine future outcome — chosen as an honest starting point for a first capstone model, not presented as the strongest possible label. A stronger version, noted but not built here, would define decline from a true past-features → future-outcome split.

Features

Seven observed, pre-decision signals: 90-day impressions, content age, days since last update, average search position, click-through rate, engagement rate, and word count. Each is knowable at the point a reviewer would actually see it — none depend on data from after the decision moment.

Signal verification

Before building any rule, two candidate signals were checked directly against outcome rates, each with sample sizes reported rather than assumed adequate:

A mixed verdict on staleness was treated as a real, useful finding rather than a failed check — it correctly predicted that the model would later assign staleness comparatively little weight (see Results).

Baseline

A transparent, hand-written rule combining staleness, demand, and decline signals into a single score, with reason codes explaining each flag (stale_visible_page, declining_with_demand, low_ctr_visible_page). An early version of this baseline was found, during its own top-20 manual review, to include trend_direction directly in the score — the same field used to build the label — inflating precision@50 to a false 1.00. This was caught, the leaked term removed, and the corrected baseline (precision@50 = 0.30) is the one reported throughout this paper.

Model

Random Forest, chosen because the seven features plausibly interact non-linearly (e.g. staleness may only matter when demand is also high) in ways a linear rule cannot represent, and because tree-based methods showed the strongest lift in this lane's own reference pipeline.

Validation design

A client-grouped split (80/20) was used, holding every page from a given client entirely in either train or test. This matters because pages from the same client can share stylistic and structural patterns a model could partially memorize rather than genuinely learn from signal — inflating apparent performance on a naive random split. This was tested directly, not assumed (see Results).

Leakage checks

  • No feature is calculated after the decision point, and no feature window overlaps the label's own computation.
  • No product-computed field was available to leak, since none exist in this dataset.
  • The label-derived leak in the baseline score (above) was found and removed.
  • Client-grouped splitting prevents the same client's pages from appearing in both train and test.

Under a naive random split, the model reports an AUC of 0.753 — a seemingly strong result. Under the honest client-grouped split, it drops to 0.587, much closer to chance. The gap shows the naive split let the model partly recognize client-specific patterns already seen in training, rather than learning signal that transfers to a genuinely new client. 0.587 is the number this paper treats as the trustworthy estimate.

05

Limitations & Honest Framing

  • Correlation, not causation. This work shows the model ranks better than the rule at identifying pages that recently declined — it does not show that refreshing a flagged page causes recovery. No experiment was run.
  • Same-window label. The label reflects a same-window definition of decline, not a true future outcome. A stronger version would use a past-features → future-outcome split.
  • Precision, not certainty. At precision@50 = 0.66, roughly one in three flagged pages in the top 50 will not be a genuine case — reviewers should expect and plan for that error rate.
  • One dataset, one snapshot. Validated on a 30,000-row, 32-client starter sample. Not tested on live, ongoing production data or on clients/industries outside this sample.
  • No causal design. Nothing here establishes that acting on a recommendation improves outcomes — this is decision-support for a human reviewer, not an autonomous action system.

A finding from the review process itself

Manually reviewing the top 20 queue entries surfaced a real scoring bug: several pages with almost no traffic (30–95 impressions, 0% CTR) scored nearly as high as genuinely flagged pages, because the scoring formula weighted staleness and demand independently of whether any rule condition had actually triggered. The fix — scoring only pages that meet at least one real condition — is a concrete example of why a ranked queue needs a human skim before it is trusted, not just a good average metric.

What should never be automated

  • Publishing or editing live content without a human reviewing the recommendation first.
  • Removing or merging pages based solely on the model's score — this carries business and SEO risk a model score alone cannot justify.
  • Presenting the model's output as a client-facing performance claim, or as proof a page "failed."
  • Telling a client that refreshing a page will cause recovery — no causal design supports that claim.
